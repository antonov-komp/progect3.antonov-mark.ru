## Цель

Мигрировать хранение событий исходящих вебхуков с файловой системы на SQLite базу данных для улучшения производительности, масштабируемости и функциональности модуля.

## Контекст

Текущая система хранит события в файлах:
- `logs/{EVENT_TYPE}/raw.json` — полный payload события (маскированный)
- `logs/{EVENT_TYPE}/event.log` — лог-файл с краткой информацией
- `logs/{EVENT_TYPE}/task-details.log` или `comment-details.log` — детали задачи/комментария
- `logs/{EVENT_TYPE}/enriched.json` — обогащенные данные (опционально)
- `queue/pending/*.json` — очередь обработки
- `logs/state/{entityId}.json` — состояния сущностей

Переход на SQLite позволит:
- Использовать индексы для быстрого поиска событий
- Выполнять сложные SQL-запросы (JOIN, GROUP BY, агрегации)
- Улучшить производительность при больших объемах данных
- Упростить аналитику и отчетность
- Обеспечить целостность данных через транзакции

## Технические требования

### SQLite специфика

- **Версия:** SQLite 3.x (встроен в PHP)
- **Расширение PHP:** PDO_SQLITE
- **WAL режим:** Включен для лучшей производительности (`PRAGMA journal_mode=WAL`)
- **Размер БД:** Практически неограничен (до 140 TB, но практически ограничен размером файла)
- **Параллельная запись:** Ограничена (WAL режим помогает, но не решает полностью)

### Производительность

- **Целевая нагрузка:** < 50 событий/сек
- **Объем данных:** < 100,000 событий/день
- **Размер БД:** Рост ~1-5 MB/день (зависит от размера payload)

### Ограничения SQLite

- Один файл БД (может быть узким местом)
- Ограниченная параллельная запись
- Нет репликации
- Не подходит для очень высоких нагрузок (> 100 событий/сек)

## Риски и митигация

### Риск 1: Потеря данных при миграции

**Митигация:**
- Резервное копирование файлов перед миграцией
- Постепенная миграция (старые данные остаются в файлах)
- Валидация данных после миграции
- Транзакции для атомарности операций

### Риск 2: Снижение производительности

**Митигация:**
- Использование WAL режима
- Оптимизация индексов
- Батч-вставки при миграции
- Профилирование запросов

### Риск 3: Блокировки при параллельной записи

**Митигация:**
- WAL режим уменьшает блокировки
- Таймауты для операций записи
- Retry логика при блокировках
- Ограничение параллельной записи на уровне приложения

### Риск 4: Рост размера БД

**Митигация:**
- Политика архивации старых данных
- Периодическая очистка старых записей
- Мониторинг размера БД

## Вопросы/ответы

- Q: Нужно ли удалять старые файлы после миграции?  
  A: Нет, файлы остаются для истории и как резервная копия.

- Q: Что делать если SQLite файл поврежден?  
  A: Восстановление из резервной копии или миграция заново из файлов.

- Q: Можно ли использовать SQLite для продакшена?  
  A: Да, если нагрузка < 50 событий/сек и объем < 100K событий/день.

- Q: Нужна ли репликация?  
  A: Нет, SQLite не поддерживает репликацию. Для репликации нужен MySQL (TASK-026).
