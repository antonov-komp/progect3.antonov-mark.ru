# TASK-006: Единый Bitrix24 REST‑клиент

Дата: 2026-01-14 23:35 (UTC+3, Брест)
Статус: done
Приоритет: high
Исполнитель: Backend PHP (Bitrix24 REST)

## Цель
Ввести единый REST‑клиент для Bitrix24, обеспечивающий унифицированную обработку ошибок и совместимость с текущим `CRest`.

## Контекст
REST‑вызовы сейчас выполняются внутри сервисов напрямую (через `CRest` и custom token‑логику). Это приводит к дублированию кода и разной обработке ошибок.

## Требования
### Функциональные
- Создать сервис‑клиент, который поддерживает:
  - вызовы через `CRest`;
  - вызовы по токену `AUTH_ID`/`DOMAIN` (из контекста запроса).
- Централизовать обработку ошибок и нормализацию ответа.
- Добавить единый слой логирования ошибок REST.

### Нефункциональные
- PSR‑12.
- Ошибки REST не прерывают основной сценарий (возвращаем структурированную ошибку).
- Не хранить секреты в коде.

## Границы работ
### Входит
- Единый клиент для REST‑вызовов.
- Унификация ошибок и логирование.
- Поддержка `AUTH_ID`/`DOMAIN` и `CRest` режимов.

### Не входит
- Рефактор логики в `app/crest.php` (только обёртка).
- Изменение формата `ui-state` ответа.

## Модули/компоненты
- `app/crest.php`
- Новый сервис: `app/Services/Bitrix24Client.php`
- Потребители: сервисы пользовательского профиля/приветствия (см. TASK‑005).

## Зависимости (иерархия)
1. `app/crest.php` — базовый REST‑клиент.
2. `app/Services/*` — вызовы REST.
3. `app/api/ui-state.php` — формат ответа.

## Этапы
1. Спроектировать интерфейс `Bitrix24Client` (method, params, authContext).
2. Реализовать стратегии вызова:
   - через `CRest::call`;
   - через direct REST URL c `AUTH_ID`.
3. Унифицировать ошибки:
   - `error`, `error_information`;
   - HTTP‑ошибки и ошибки JSON‑декодирования.
4. Внедрить клиент в сервисы (поэтапно).

## Контракт клиента (пример)
`call(string $method, array $params = [], array $authContext = []): array`

`$authContext`:
- `auth_id`: `string`
- `domain`: `string`

Ответ (минимум):
- `result`: `array|bool|null`
- `error`: `string` (если есть)
- `error_information`: `string` (если есть)

## API‑методы Bitrix24
- `user.current` — https://context7.com/bitrix24/rest/user.current
- `user.get` — https://context7.com/bitrix24/rest/user.get
- `department.get` — https://context7.com/bitrix24/rest/department.get
- `user.admin` — https://context7.com/bitrix24/rest/user.admin

## Технические требования
- Логировать ошибки через `AddMessage2Log` или `error_log`.
- Валидировать домен (только латиница, цифры, `.` и `-`).
- Защититься от невалидного JSON.
- Таймауты должны быть ограничены (например, 10–30 сек).

## Критерии приемки
- Все REST‑вызовы выполняются через единый клиент.
- Ответы REST имеют единый формат ошибок.
- Отсутствуют дублирующие блоки cURL.
- При невалидном JSON возвращается структурированная ошибка.

## Пример (псевдокод)
```php
$client = new Bitrix24Client($authContext);
$result = $client->call('user.current');
```

## Тестирование
- Вызов REST с `AUTH_ID`/`DOMAIN`.
- Вызов REST без `AUTH_ID` (через `CRest`).
- Проверка обработки сетевых ошибок и невалидного JSON.
- Проверка домена с недопустимыми символами (ожидается ошибка).
