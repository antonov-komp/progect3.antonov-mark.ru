## TASK-002: Конфигурация доступа к REST-приложению по контексту открытия

**Дата:** 2026-01-14 22:20 (UTC+3, Брест)  
**Статус:** done  
**Приоритет:** high  
**Роль/Исполнитель:** Технический писатель (подготовка), далее Backend (PHP/Bitrix24)  

### Цель
Добавить четкую конфигурацию, которая управляет доступом к REST‑приложению по контексту открытия: глобально закрыть доступ, закрыть доступ только по прямой ссылке, либо закрыть доступ только внутри Bitrix24.

### Контекст
Приложение уже корректно определяет, кто его открывает и где (внутри Bitrix24 или по прямой ссылке). Требуется единая точка управления через конфиг, чтобы администратор мог быстро ограничивать доступ.

### Бизнес-ценность
Управляемость доступа без изменения кода, снижение рисков несанкционированного использования.

### Область применения
- Все входы в приложение (стартовая страница и любые будущие экраны) должны проходить проверку конфигурации.
- Проверка выполняется до формирования основного UI, но после определения контекста открытия.

## Требования

### Функциональные
1. Конфиг должен поддерживать глобальный запрет доступа с сообщением: `Приложение закрыто для входа Администратором`.
2. Конфиг должен поддерживать запрет доступа только при открытии по прямой ссылке (вне Bitrix24).
3. Конфиг должен поддерживать запрет доступа только при открытии внутри Bitrix24.
4. Сообщение о запрете должно выводиться в UI вместо основного контента.
5. При запрете логика определения контекста все равно должна выполняться (для логирования).
6. При неизвестном режиме конфигурации должен применяться безопасный дефолт `deny_all` с логированием причины.
7. Сообщение о запрете должно быть экранировано (защита от XSS).

### Нефункциональные
1. Проверка доступа должна быть централизована в сервисе/классе.
2. Логировать факт запрета (контекст, причина, конфиг‑режим).
3. Не хранить секреты в конфиге.
4. Соблюдать PSR‑12 для PHP‑кода.
5. Ошибки чтения конфига не должны ломать приложение (использовать дефолт и логировать).

## Технические требования
### Формат конфигурации
Файл `app/config/app-access.php` должен возвращать массив:
```php
<?php

return [
    // Возможные режимы:
    // - allow_all: доступ разрешен везде
    // - deny_all: глобальный запрет
    // - deny_direct: запрет при открытии по прямой ссылке
    // - deny_embedded: запрет при открытии внутри Bitrix24
    'mode' => 'allow_all',
    'deny_message' => 'Приложение закрыто для входа Администратором',
];
```

### Правила применения
1. `deny_all` — всегда показывать `deny_message`.
2. `deny_direct` — показывать `deny_message` только при `access=direct`.
3. `deny_embedded` — показывать `deny_message` только при `access=embedded`.
4. `allow_all` — доступ без ограничений.
5. Любой неизвестный режим — эквивалент `deny_all` + запись в лог с причиной `invalid_mode`.

### Определение контекста доступа
- `access=embedded` — приложение открыто внутри Bitrix24.
- `access=direct` — приложение открыто напрямую по ссылке вне Bitrix24.
- Если контекст не определен, считать `access=direct` и логировать `access=unknown`.

### Формат логирования запрета
Добавить в лог поля:
- `access_mode` — значение из конфига.
- `access_context` — embedded/direct/unknown.
- `access_decision` — allow/deny.
- `access_reason` — deny_all|deny_direct|deny_embedded|invalid_mode|config_error.
Запись должна дополнять существующий формат лога `app-open.log` (без хранения секретов).

### Приоритеты и дефолты
- Источник правды — файл `app/config/app-access.php`.
- Дефолтные значения (если файл не найден/поврежден):
  - `mode=deny_all`
  - `deny_message=Приложение закрыто для входа Администратором`

## Критерии приёмки
1. При `mode=deny_all` приложение всегда показывает строку запрета.
2. При `mode=deny_direct` приложение запрещено только при открытии по прямой ссылке.
3. При `mode=deny_embedded` приложение запрещено только при открытии внутри Bitrix24.
4. При `mode=allow_all` приложение работает как сейчас.
5. В логах фиксируется причина запрета и контекст открытия.
6. При некорректном режиме — доступ запрещен, причина `invalid_mode` фиксируется в логе.
7. При отсутствии/повреждении файла конфига — доступ запрещен, причина `config_error` фиксируется в логе.

---

## Тестирование
- `mode=deny_all`: открыть по прямой ссылке и внутри Bitrix24 — в обоих случаях запрещено.
- `mode=deny_direct`: открыть по прямой ссылке — запрещено, внутри Bitrix24 — разрешено.
- `mode=deny_embedded`: открыть внутри Bitrix24 — запрещено, по прямой ссылке — разрешено.
- `mode=allow_all`: оба контекста — разрешено.
- Проверить запись в `logs-apps/YYYY/MM/DD/app-open.log` для каждого случая.
- Повредить файл конфига (синтаксическая ошибка) — доступ запрещен, причина `config_error`.
- Указать `mode=deny_something` — доступ запрещен, причина `invalid_mode`.
