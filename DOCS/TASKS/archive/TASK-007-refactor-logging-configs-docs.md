# TASK-007: Логирование, конфиги, документация

Дата: 2026-01-14 23:35 (UTC+3, Брест)
Статус: done
Приоритет: medium
Исполнитель: Backend PHP (Bitrix24 REST)

## Цель
Унифицировать логирование и конфигурации доступа, а также обновить документацию после рефакторинга сервисов.

## Контекст
Логирование распределено по нескольким сервисам, часть логики дублируется. Конфиг доступа хранит режимы, но не имеет строгой валидации и документации поведения.

## Требования
### Функциональные
- Вынести логирование в общий сервис/utility.
- Использовать единые правила очистки и форматирования логов.
- Зафиксировать и описать режимы доступа в конфиге.
- Обновить архитектурную документацию с новыми сервисами.

### Нефункциональные
- PSR‑12.
- Логирование не прерывает основной сценарий.
- Секреты не хранятся в коде и документации.

## Границы работ
### Входит
- Единый логгер (utility/сервис).
- Централизация формата логов.
- Валидация режимов доступа.
- Обновление архитектурной документации.

### Не входит
- Изменение бизнес‑логики доступа.
- Миграция логов/архивация (отдельная задача при необходимости).

## Модули/компоненты
- `app/Services/AccessControlService.php`
- `app/Services/UserGreetingService.php` (или новые сервисы после TASK‑005)
- `app/config/app-access.php`
- `DOCS/ARCHITECTURE/tech-stack.md`

## Зависимости (иерархия)
1. TASK‑005 (сервисный слой).
2. TASK‑006 (единый REST‑клиент).
3. `logs-apps/` — текущая структура логов.

## Этапы
1. Спроектировать `AppLogger`:
   - единый формат строки;
   - безопасная очистка значений;
   - fallback `error_log`.
2. Перевести сервисы на новый логгер.
3. Обновить `app/config/app-access.php`:
   - валидировать режим;
   - описать режимы в комментариях.
4. Обновить `DOCS/ARCHITECTURE/tech-stack.md`:
   - список сервисов;
   - правила логирования.

## Контракт логгера (пример)
`log(string $channel, array $context): void`

Обязательные поля `context`:
- `timestamp`
- `portal_id`
- `status`
- `message`
- `access_context`

## Валидация режимов доступа
Допустимые значения:
- `allow_all`
- `deny_all`
- `deny_direct`
- `deny_embedded`

## API‑методы Bitrix24
Не используются напрямую.

## Технические требования
- Лог‑директории создаются безопасно (775).
- Не допускать `\r`/`\n` в лог‑строках.
- Отказ записи в лог не должен ломать основной поток.

## Критерии приемки
- Все записи логов проходят через единый сервис.
- Конфиг доступа документирован и имеет проверку допустимых режимов.
- Документация актуальна и отражает новый сервисный слой.
- Логирование не падает при ошибке записи в файл.

## Пример (формат лога)
```
YYYY-MM-DD HH:MM (UTC+3, Brest) | user_id=... | portal_id=... | status=... | message=...
```

## Тестирование
- Проверка логирования при ошибках REST.
- Проверка отказа доступа и записи логов.
- Проверка корректности формата даты (Брест, UTC+3).
- Проверка невалидного режима в `app-access.php`.
