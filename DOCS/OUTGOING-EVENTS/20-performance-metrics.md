# Производительность и метрики модуля outgoing-webhook

**Дата создания:** 2026-01-26 (UTC+3, Брест)  
**Версия:** 1.0

## Назначение

Документ описывает метрики производительности модуля `outgoing-webhook`: метрики обработки очереди, метрики ActivityFirst, производительность REST-запросов, рекомендации по оптимизации.

---

## Метрики обработки очереди

### Источник метрик

**Файл:** ответ от `process-queue.php` или `process-queue-cli.php`

**Формат:**
```json
{
  "processed": 10,
  "processingMs": 5000,
  "queue": {
    "pending": 5,
    "processing": 0,
    "done": 100,
    "failed": 2
  }
}
```

### Описание метрик

#### processed

**Тип:** `int`  
**Описание:** Количество обработанных заданий за запуск

**Типичные значения:**
- Низкая нагрузка: 5-20 заданий
- Средняя нагрузка: 20-50 заданий
- Высокая нагрузка: 50-100 заданий

#### processingMs

**Тип:** `int`  
**Описание:** Время обработки в миллисекундах

**Типичные значения:**
- 50 заданий: 10-25 секунд (10000-25000 мс)
- 100 заданий: 20-50 секунд (20000-50000 мс)

**Факторы:**
- Тип событий (с загрузкой справочников обрабатываются дольше)
- Сетевая задержка к Bitrix24
- Размер данных сущностей

#### queue.pending

**Тип:** `int`  
**Описание:** Количество заданий, ожидающих обработки

**Мониторинг:**
- Если постоянно растёт — обработчик не успевает
- Если постоянно 0 — обработчик работает быстрее, чем приходят события

#### queue.processing

**Тип:** `int`  
**Описание:** Количество заданий, находящихся в обработке

**Мониторинг:**
- Обычно 0 (обработка синхронная)
- Если > 0 и не уменьшается — возможны зависшие задания

#### queue.done

**Тип:** `int`  
**Описание:** Количество успешно обработанных заданий

**Мониторинг:**
- Растёт со временем
- Можно использовать для подсчёта общего количества обработанных событий

#### queue.failed

**Тип:** `int`  
**Описание:** Количество заданий, завершившихся с ошибкой

**Мониторинг:**
- Должно быть минимальным
- Если растёт — нужно анализировать причины ошибок

## Метрики ActivityFirst

### Источник метрик

**Файл:** `logs/activity-first-metrics.log`

**Формат:** line-based JSON

### Формат записи (успех)

```json
{
  "loggedAt": "2026-01-26T12:00:00+03:00",
  "requestId": "abc123...",
  "taskId": "123",
  "sync": true,
  "durationMs": 1500,
  "success": true,
  "filesCount": 2,
  "dealsCount": 1,
  "rateLimitHit": false
}
```

### Формат записи (ошибка)

```json
{
  "loggedAt": "2026-01-26T12:00:00+03:00",
  "requestId": "abc123...",
  "taskId": "123",
  "sync": true,
  "durationMs": 500,
  "success": false,
  "error": "Invalid fileId: abc"
}
```

### Формат записи (rate limit)

```json
{
  "loggedAt": "2026-01-26T12:00:00+03:00",
  "requestId": "abc123...",
  "taskId": "123",
  "sync": true,
  "durationMs": 0,
  "success": false,
  "error": "rate_limit_exceeded",
  "rateLimitHit": true
}
```

### Описание метрик

| Поле | Тип | Описание |
|------|-----|----------|
| `loggedAt` | string | Время логирования (ISO 8601) |
| `requestId` | string | ID запроса |
| `taskId` | string | ID задачи |
| `sync` | bool | Синхронная обработка (`true`) |
| `durationMs` | int | Время обработки в миллисекундах |
| `success` | bool | Успешность обработки |
| `filesCount` | int | Количество файлов (только при успехе) |
| `dealsCount` | int | Количество сделок (только при успехе) |
| `rateLimitHit` | bool | Был ли превышен rate limit |
| `error` | string | Описание ошибки (только при ошибке) |

### Типичное время обработки

**Компоненты:**
- Прикрепление файлов к задаче: 200-500 мс на файл
- Загрузка файла в Base64: 100-300 мс на файл
- Обновление файлов сделки: 300-800 мс на сделку

**Общее время:**
- 1 файл, 1 сделка: 600-1600 мс
- 2 файла, 1 сделка: 900-2100 мс
- 2 файла, 2 сделки: 1200-3200 мс

## Производительность REST-запросов

**Поле:** `source.responseTimeMs`

**Формат:**
```json
{
  "source": {
    "method": "crm.deal.get",
    "responseTimeMs": 240
  }

```

## Логирование шагов очереди

### Источник метрик

**Файл:** `logs/queue-steps.log`

**Формат:** line-based JSON

### Формат записи (начало)

```json
{
  "loggedAt": "2026-01-26T12:00:00+03:00",
  "step": "started",
  "requestId": "abc123...",
  "eventType": "ONTASKADD",
  "entityType": "task",
  "entityId": "123",
  "attempt": 1,
  "jobFile": "20260126_120000_ONTASKADD_123.json"
}
```

### Формат записи (завершение)

```json
{
  "loggedAt": "2026-01-26T12:00:05+03:00",
  "step": "finished",
  "requestId": "abc123...",
  "eventType": "ONTASKADD",
  "entityType": "task",
  "entityId": "123",
  "attempt": 1,
  "jobFile": "20260126_120000_ONTASKADD_123.json",
  "status": "done"
}
```

**Возможные статусы:**
- `done` — успешно обработано
- `failed` — ошибка обработки
- `skipped` — пропущено (например, уже обработано синхронно)

### Анализ производительности

**Расчёт времени обработки:**
```bash
# Найти записи для конкретного requestId
grep "abc123" logs/queue-steps.log | jq -s '.[0].loggedAt, .[1].loggedAt'
```

**Подсчёт успешных/неуспешных:**
```bash
# Успешные
grep '"status":"done"' logs/queue-steps.log | wc -l

# Неуспешные
grep '"status":"failed"' logs/queue-steps.log | wc -l
```

## Рекомендации по оптимизации

### Настройка лимита заданий

**Рекомендации:**
- **Низкая нагрузка:** 20-50 заданий
- **Средняя нагрузка:** 50-100 заданий
- **Высокая нагрузка:** 100-200 заданий

**Зависит от:**
- Времени обработки одного задания
- Таймаута PHP
- Производительности сервера

### Частота запуска обработчика

**Рекомендации:**
- **Низкая нагрузка:** каждые 5-10 минут
- **Средняя нагрузка:** каждые 2-5 минут
- **Высокая нагрузка:** каждую минуту

**Формула:**
```
Частота = (Среднее время обработки задания * Лимит) / 2
```

### Оптимизация REST-запросов

1. **Кеширование справочников:**
   - TTL: 24 часа (86400 секунд)
   - Уменьшает количество запросов к Bitrix24

2. **Повторные попытки:**
   - Настройка: `OUTGOING_WEBHOOK_REST_RETRIES=2`
   - Задержка: `OUTGOING_WEBHOOK_REST_RETRY_DELAY_MS=1000`

3. **Параллельная обработка:**
   - Не поддерживается (обработка последовательная)
   - Можно запускать несколько обработчиков параллельно (осторожно!)

### Оптимизация файловых операций

1. **Использование блокировок:**
   - `flock()` для безопасной записи
   - Явная синхронизация через `fflush()`

2. **Оптимизация записи:**
   - Запись в JSON с форматированием только для отладки
   - В продакшене можно убрать `JSON_PRETTY_PRINT`

### Мониторинг производительности

**Рекомендуется:**
1. Регулярно проверять метрики очереди
2. Анализировать время обработки заданий
3. Мониторить количество failed-заданий
4. Отслеживать метрики ActivityFirst

**Пример скрипта мониторинга:**
```bash
#!/bin/bash
# Проверка метрик очереди
RESULT=$(curl -s "https://your-domain.com/outgoing-webhook/tools/process-queue.php?limit=50")
PENDING=$(echo $RESULT | jq '.queue.pending')
FAILED=$(echo $RESULT | jq '.queue.failed')

if [ "$PENDING" -gt 100 ]; then
    echo "WARNING: Too many pending jobs: $PENDING"
fi

if [ "$FAILED" -gt 10 ]; then
    echo "WARNING: Too many failed jobs: $FAILED"
fi
```
